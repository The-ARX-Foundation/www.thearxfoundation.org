Privacy-Preserving Verification

The Tracking Problem

Why QR Codes Dox Users

Data Leaked by Standard QR Verification

Data PointHow It's CapturedRisk
Device IDUser-Agent string, screen resolution, browser fingerprintPermanent tracking across sessions
IP AddressHTTP request to brand's COA serverApproximate location (city-level)
GPS CoordinatesPhone OS permission prompt if site requestsExact location
TimestampServer logs when COA is accessedUsage patterns, frequency
Batch NumberURL parameter or form submissionLinks identity to specific purchase

Result: Brand knows who bought what, where, when. User has zero privacy.

Why Brands Want This Data

  • Retargeting ads (sell to data brokers)
  • Geographic demand mapping
  • Batch recall targeting (identify affected customers)
  • Law enforcement cooperation (if pressured)
Core Requirement

Users must verify batch authenticity without revealing identity. Brands must prove batch legitimacy without tracking lookups.

Privacy-Preserving Solutions

Ranked by Simplicity

Tier 1: Static File Hosting (Simplest)

Architecture

Batch number printed on package (no QR). User manually types into privacy-focused browser. COA served as static PDF from CDN.

Example URL:

https://brand.com/coa/batch-SD241227-037.pdf

Tech Stack:

  • CDN: Bunny CDN (privacy-respecting, no tracking)
  • No backend — just static files
  • No analytics — no Google, no Cloudflare tracking mode

Zero tracking if configured correctly

Requires manual batch entry

Tier 2: IPFS + Blockchain (Better)

Zero-Knowledge Batch Verification

How it works:

  1. Brand uploads COA to IPFS (decentralized storage)
  2. Brand publishes hash(batch_data) → IPFS_CID to Polygon smart contract
  3. QR code contains batch hash (not batch number)
  4. User scans → visits neutral site (arxverify.org)
  5. Site queries smart contract (client-side, no server)
  6. Contract returns IPFS link
  7. User downloads COA from IPFS (peer-to-peer)

Tech Stack:

  • IPFS for COA hosting
  • Polygon L2 for smart contract (cheap, fast)
  • Client-side web3.js (no backend server)

Brand can't track lookups

Data is immutable

Requires crypto infrastructure

Smart Contract Example
// Solidity (Polygon)
contract BatchVerify {
  mapping(bytes32 => string) public batches;
  
  function addBatch(bytes32 _hash, string memory _ipfsCID) public {
    batches[_hash] = _ipfsCID;
  }
  
  function getCOA(bytes32 _hash) public view returns (string memory) {
    return batches[_hash];
  }
}

Tier 3: ZK-SNARKs (Maximum Privacy)

Merkle Tree + Zero-Knowledge Proofs

Concept: User proves "I have a valid batch" without revealing which batch.

How it works:

  1. Brand creates Merkle tree of all batches
  2. Publishes Merkle root on-chain
  3. User receives Merkle proof (QR code or NFC)
  4. User submits proof to verifier (smart contract or local)
  5. Verifier confirms: "Valid batch" without learning batch number

Maximum privacy

Complex implementation

Requires ZK circuit (SnarkJS, Circom)

NFC + Tor Architecture

Instant Scan, Zero Tracking

Option 1: NFC → Tor Hidden Service

User Flow
  1. Tap NFC tag → Reads .onion URL + batch ID
  2. Phone opens Tor Browser (Android: Orbot + Tor Browser)
  3. Queries arxverify.onion over Tor
  4. COA delivered (IP hidden, no location leak)

NFC Tag Contents:

arxverify.onion/batch/7a3f9b2c8e4d

Tor hides user location

Requires Tor Browser on phone

Slow (Tor latency)

Option 2: NFC → IPFS Hash (Offline Read)

User Flow
  1. Tap NFC → Reads IPFS CID (content hash)
  2. Phone stores CID locally (no network request yet)
  3. User manually visits IPFS gateway when ready
  4. Pastes CID → Downloads COA

NFC Tag Contents:

QmT5NvUtoM5nWFfrQdVrFtvGfKFmG7AHE8P34isapyhCxX

NFC read is offline (no tracking)

User controls when to fetch

Requires manual gateway visit

Option 3: NFC → Encrypted COA (Fully Offline)

User Flow
  1. Tap NFC → Reads encrypted COA blob
  2. User types batch number into local app
  3. App derives decryption key from batch number
  4. COA decrypted entirely offline

Encryption:

key = PBKDF2(batch_number, salt)
coa_decrypted = AES256.decrypt(nfc_data, key)

NFC Storage: 888 bytes (NTAG216) — enough for compressed JSON or link to IPFS

Zero network request

Zero tracking

Requires app

ARX Verify — Build Specification

Open Source, Privacy-First

Recommended Architecture

Core Design

NFC tag stores IPFS CID. Smart contract maps batch hash → IPFS link. Static site queries contract client-side. Zero backend.

Layer 1: Packaging
  • NFC tag: NTAG216 (888 bytes, $0.18/tag bulk)
  • Tag contains: batch_hash + IPFS_CID
  • Printed batch number on package (human-readable backup)
Layer 2: COA Hosting
  • All COAs uploaded to IPFS (decentralized storage)
  • Smart contract on Polygon L2 (cheap gas fees)
  • Contract stores: keccak256(batch_data) → IPFS_CID
  • Contract is read-only, public, immutable
Layer 3: Verification Site
  • Static HTML/JS hosted on IPFS + Tor mirror
  • No analytics, no tracking, no backend server
  • User pastes batch hash → Site queries contract (client-side)
  • Contract returns IPFS CID → Site fetches COA from IPFS

User Flow

  1. User taps NFC tag → Phone reads batch_hash
  2. User visits arxverify.org (or arxverify.onion via Tor)
  3. Pastes hash into lookup form
  4. Site calls Polygon contract (web3.js, client-side)
  5. Contract returns IPFS CID
  6. Site fetches COA from IPFS gateway
  7. COA displayed (PDF or JSON)

Smart Contract Code

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract ARXBatchVerify {
    mapping(bytes32 => string) public batches;
    address public owner;
    
    event BatchAdded(bytes32 indexed batchHash, string ipfsCID);
    
    constructor() { owner = msg.sender; }
    
    function addBatch(bytes32 _hash, string memory _cid) public {
        require(msg.sender == owner, "Not authorized");
        batches[_hash] = _cid;
        emit BatchAdded(_hash, _cid);
    }
    
    function getCOA(bytes32 _hash) public view returns (string memory) {
        return batches[_hash];
    }
}

Frontend Code (Static Site)

// Client-side verification (no server)
import Web3 from 'web3';

const CONTRACT_ADDRESS = '0x...';
const POLYGON_RPC = 'https://polygon-rpc.com';
const web3 = new Web3(POLYGON_RPC);

async function verifybatch(batchHash) {
  const contract = new web3.eth.Contract(ABI, CONTRACT_ADDRESS);
  const ipfsCID = await contract.methods.getCOA(batchHash).call();
  
  if (!ipfsCID) return 'Batch not found';
  
  // Fetch from IPFS
  const coaURL = `https://ipfs.io/ipfs/${ipfsCID}`;
  return coaURL;
}

Privacy Guarantees

What Brand Cannot Track
  • Who looked up a batch (contract queries are public blockchain reads)
  • User IP address (if accessed via Tor or privacy browser)
  • User location (no GPS, no server logs)
  • Device fingerprint (client-side only, no analytics)
What Brand Can See
  • Total lookup count per batch (via blockchain explorer)
  • Timestamp of lookups (blockchain transaction time)

Note: These are aggregate metrics, not user-specific.

Alternative: Blind Signatures

Maximum Privacy Protocol

Concept: User gets COA without brand knowing which batch they looked up.

  1. User blinds batch hash: blinded = blind(batch_hash, random)
  2. User sends blinded hash to brand server
  3. Brand signs blinded hash (proves it's valid) without seeing original
  4. User unblinds signature: sig = unblind(blinded_sig, random)
  5. User submits (batch_hash, sig) to neutral third party
  6. Third party verifies signature → returns COA

Tech: RSA blind signatures (Privacy Pass protocol)

Brand can't link signature to user

Requires backend server for signing
