§ 01Project Overview

⌨ Unexpected Keyboard + Mandarin

Fork Unexpected Keyboard → add Pinyin input + sentence-level autocorrect → optimize for Onyx Boox daily driver. Local-first, 100% offline, ARX open-source ethos.

Quick start. Unexpected Keyboard already excels at corner-swipe efficiency. We're adding: (1) Pinyin layout with tone marks in corners, (2) hanzi candidate selection, (3) local LLM inference for sentence-level correction, (4) e-ink optimization for Boox grayscale display.

Status: Architecture documented. Phase 1 (fork + Pinyin layout) ready to begin. Daemon integration (Phase 2) depends on Hetzner cloud deployment.

Core mission: Input method that respects privacy, supports non-Latin scripts natively, and works offline. No cloud typing surveillance.
§ 1.1Key Facts

Base: Unexpected Keyboard (Kotlin, F-Droid)
Language: Mandarin (Pinyin input method)
Target Device: Onyx Boox 7"/10" (e-ink, Wacom digitizer)
Autocorrect: TinyLlama-1.1B (on-device) or Mistral-7B (daemon-assisted)
Status: Active design phase
Repository: github.com/ARX-Foundation/unexpected-keyboard-mandarin

Tags: input-method, mandarin, boox, open-source, llm, privacy
§ 02Architecture & Paths

Two implementation paths. Path B (daemon-assisted) recommended initially—leverages existing ARXd/Hetzner infrastructure. Path A (on-device) available as fallback for latency-critical sessions.

§ 2.1Path A: On-Device LLM

Local-Only Inference

Boox device: ├── Unexpected Keyboard (modified) │ └── Sends typed text → /tmp/kbd_inference.sock ├── Termux background service │ └── TinyLlama-1.1B-q4 (~500MB) └── Keyboard renders correction → update e-ink once
Pros:
  • Zero network dependency
  • Works completely offline
  • No server operations
Cons:
  • Slow inference (1-3s per sentence on Snapdragon 680)
  • Battery drain from background LLM
  • Model quality limited (1.1B < 7B)
§ 2.2Path B: Daemon-Assisted (Recommended)

Cloud-Accelerated via Hetzner

Boox device: └── Unexpected Keyboard (modified) └── Sends typed text → Hetzner MCP daemon (SSH over Tailscale) Hetzner VPS: ├── MCP server (Python/Node) │ └── "correct_mandarin_sentence" tool ├── Ollama or vLLM │ └── Mistral-7B (better Mandarin) └── Returns single corrected sentence Keyboard renders → e-ink update once
Pros:
  • Faster inference (GPU acceleration)
  • Better model quality (7B)
  • Leverages existing infra
  • Shareable daemon across devices
Cons:
  • Network dependency (Tailscale mesh mitigates)
  • Adds server operations
§ 2.3Data Flow
User types: "我喜欢吃苹果。" (I like to eat apples) ↓ Keyboard detects sentence terminal (。) ↓ Sends to daemon: {pinyin: "wo3 xi3huan5 chi1 ping2guo3"} ↓ MCP tool: correct_mandarin_sentence(pinyin) ↓ LLM checks tone/typos → returns corrected hanzi ↓ Keyboard receives: "我喜欢吃苹果。" ↓ Update e-ink once (A2 mode, 150ms refresh) ↓ User sees correction with visual cue (corner flash + haptic)
Recommendation: Path B initially, with Path A as e-ink-optimized fallback.
§ 03Constraints & Design Decisions
§ 3.1E-Ink Specific

Refresh lag: Rapid updates cause ghosting. LLM streaming suggestions = visual garbage on e-ink.

Touch latency: Wacom digitizer adds 50-200ms. Compound redraws with lag.

Color: Most Boox are grayscale/6-color. Typography matters more than fancy UI.

Performance: Boox typically Snapdragon 680+ (adequate for quantized LLM).

Solution: Single-fire suggestions (compute once, render once) instead of streaming.

§ 3.2Mandarin Input UX

Pinyin swipe: Compatible with corner-swipe model. Swipe northeast/southeast corners for tone marks (1-4, neutral).

Hanzi selection: After typing pinyin, tap/swipe candidate bar to select character.

No existing solution: No FOSS keyboard has sentence-level Pinyin + character autocorrect. We're building something net-new.

§ 3.3iOS Parity

akifkeyboard: Unmaintained.

KeyboardKit: Modern framework, but Apple sandbox is strict (no IPC outside app, limited text rewriting).

Status: iOS mirror possible but limited feedback vs Android. Defer until iOS MCP equivalent exists.

Priority: Android first (Boox daily driver). iOS deferred.
§ 04Implementation Roadmap
§ 4.1Phase 1: Foundation (2 weeks)

Deliverables:

  • Fork Unexpected Keyboard to github.com/ARX-Foundation/unexpected-keyboard-mandarin
  • Add Pinyin layout (corner swipes for tones)
  • Add hanzi candidate bar (tap/swipe selection)
  • Test on Boox 7" device
§ 4.2Phase 2: Autocorrect Daemon (3 weeks)

Deliverables:

  • MCP server (Python + anthropic SDK or local Ollama)
  • Tool: correct_mandarin_sentence(pinyin) → hanzi
  • Deploy on Hetzner (existing VPS)
  • Keyboard client: Send to daemon, render correction once
§ 4.3Phase 3: On-Device Fallback (2 weeks)

Deliverables:

  • Bundle TinyLlama-1.1B-q4 ONNX model
  • Implement Termux socket listener
  • Fallback logic: Daemon timeout → local inference
§ 4.4Phase 4: iOS (Defer)

When iOS MCP path clears:

  • KeyboardKit base
  • Same Pinyin input + corner swipes
  • Connect to Hetzner daemon (limited feedback due to sandbox)
§ 4.5Technical Stack

Android: Kotlin, ONNX Runtime / TensorFlow Lite, MCP client, Unix socket IPC

Hetzner: Python (anthropic-sdk) or Node (MCP), Ollama/vLLM backend, Mistral-7B

Model: TinyLlama-1.1B (device fallback), Mistral-7B (daemon primary)

Total Duration: ~7 weeks (phases 1-3)
