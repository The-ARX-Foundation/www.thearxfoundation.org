§ 01Black Mirror Mesh — BLKMRR

The HDMI port is infrastructure nobody is using. Every TV in every home has one. Every TV is already plugged into power, already on a network, already trusted. BLKMRR treats that port as a community node onboarding interface — plug in a Pi Zero 2W, connect to mesh, done. No new device to explain. No new habit to form. The TV is already there.

BLKMRR is a permission-based community mesh protocol built on commodity hardware. Each node runs media serving, peer sync, federated social, and mesh routing simultaneously. The goal is local-first community infrastructure that doesn't require anyone to own a computer — just a TV.

§ 01.1The Deployment Problem No One Is Solving

Every distributed mesh project fails at the same point: onboarding. Running a node requires technical literacy, dedicated hardware, and ongoing maintenance. The result is that mesh networks stay small, stay technical, and stay irrelevant to the communities that need them most.

BLKMRR inverts this. The node is the TV adapter. If you already have a TV, your onboarding cost is the price of a Pi Zero 2W and a LibreELEC image. The same device that gives you Jellyfin and Kodi also routes your neighbor's traffic, syncs community media, and keeps a local copy of the shared knowledge base. Infrastructure that pays for itself in the same moment you install it.

Nobody uses computers anymore. But everyone has a TV. The HDMI port is the new ethernet jack.
§ 01.2ARX Lineage

FuelMesh (#72) proved the ambient sync model — devices encountering each other passively and exchanging data without user action. BLKMRR applies the same pattern at home scale: stationary nodes that sync continuously instead of opportunistically.

ARX Mesh Net (BLE local discovery, React prototype) is the event-scale version. BLKMRR is the residential-scale version. Same philosophical layer, different deployment context.

SoundWeave / ARX Open Music is the media layer. BLKMRR is the distribution substrate it runs on. The signal needs infrastructure. This is it.

DSWM (Decentralized Semantic Web Mirror) slots in as the knowledge layer — local knowledge graphs queryable without cloud. BLKMRR nodes cache DSWM snapshots and serve them to devices on the local network.

§ 01.3Name

BLKMRR — Black Mirror. The TV screen, dark and idle, hiding a node that routes your neighbor's traffic and hosts your community's media. The thing you stare at is also the thing watching the network. Not surveillance — witness. The mirror sees everything and sends nothing out.

§ 02System Architecture

Each BLKMRR node is a Pi Zero 2W running LibreELEC with a custom service layer on top. The node stack has four jobs: serve media locally, sync with peer nodes, route mesh traffic, and cache community knowledge. These run simultaneously, independently, and survive partial failures without breaking the others.

§ 02.1Service Layer

Jellyfin Active in ARX Stack

Self-hosted media server. Serves video, music, and photos to any device on the local network via browser or app. No account required, no telemetry, FOSS. The media layer the node is visible for — this is what the person installing it actually cares about in the first transaction.

Stack: Jellyfin + LibreELEC | Port: 8096 | Auth: optional local accounts

Syncthing Active in ARX Stack

Peer-to-peer file sync. Community media (music, documents, ZIM files) propagates node-to-node without a central server. When a new node comes online, it discovers peers via the mesh and begins syncing designated community folders. No coordinator, no upload limit, no cost.

Stack: Syncthing | Discovery: local broadcast + mesh peer list | Conflict: last-write-wins by default

Yggdrasil Network Buildable

End-to-end encrypted mesh routing protocol. Each node gets a cryptographic IPv6 address derived from its public key — address is permanent regardless of physical location or network. Traffic between nodes is encrypted in transit. No central directory. Scales from 2 nodes to global.

Stack: Yggdrasil 0.5.x | Address space: 200::/7 IPv6 | Peering: WiFi Direct + known peer list

Kiwix / ZIM Cache Buildable

Offline knowledge base. ZIM files (compressed Wikipedia, MDN, WikiMed, Project Gutenberg) cached locally and served over HTTP. No internet required to access. Nodes sync ZIM snapshots via Syncthing. The community's shared library lives on every node simultaneously.

Stack: Kiwix-serve | Snapshots: Wikipedia EN ~22GB, WikiMed ~2GB, MDN ~1GB | Update cadence: monthly via cron

Federated Social Layer Concept

Pixelfed (federated photo/video, Instagram-compatible) or Mastodon (federated microblogging) running as a community instance on the mesh. Each BLKMRR community runs their own instance — federation means cross-community visibility without cross-community data ownership. Pi Zero is too weak for full Mastodon; lightweight alternatives (Pleroma, Snac2) are viable at this scale.

Candidates: Snac2 (single-binary, ~10MB RAM), Pleroma | Constraint: Pi Zero 2W has 512MB RAM — Mastodon/Pixelfed need 1GB+ | Alt: shared instance on Hetzner, nodes relay
§ 02.2Network Topology

No star topology. No central server that, when it goes down, breaks everything. Each node is a full peer. If one drops, traffic reroutes around it automatically via Yggdrasil's mesh routing. The network is resilient by design — it assumes nodes will disappear and come back.

Internet optional. The mesh functions without internet access. Jellyfin serves local media, Syncthing syncs local content, Kiwix serves local knowledge. Internet connectivity adds upstream federation and external peering but is never required for the core use case.

Permission-based onboarding. Joining the mesh requires an invitation — a signed peer token distributed by an existing node operator. No open registration. Community decides who runs nodes. This is not a technical constraint, it's a social one. The protocol enforces it cryptographically via Yggdrasil key pairs.

§ 03Node Hardware Specification

The BLKMRR node is a Raspberry Pi Zero 2W running LibreELEC, installed via custom image. Form factor: credit card. Power: USB from TV. Video: mini HDMI to TV. Network: 2.4GHz WiFi onboard. No ethernet required, no external power brick, no visible cables beyond the HDMI plug itself.

§ 03.2Enclosure Design

The enclosure is a gravity-balanced flush mount designed for the back of a TV. The Pi Zero's mini HDMI sits on the short edge — a right-angle mini HDMI adapter rotates the board parallel to the TV face, enabling a thin (~15mm deep) profile that disappears behind the bezel.

Key design constraints: center of mass behind the HDMI plug axis (reduces rotational stress on port), passive vent slots on vertical faces (convection cooling without fans), micro-USB power port accessible without disassembly, optional neodymium magnet + steel plate mount for tool-free removal.

Print spec: PETG preferred over PLA for thermal tolerance near warm TVs. Textured outer surface. Two-piece snap-fit design (top cap + base). Estimated print time: 90 minutes.

§ 03.3Performance Reality Check
Pi Zero 2W is 512MB RAM, quad-core 1GHz. It will not run Mastodon, Nextcloud, or anything Java-based. Stay lean: Jellyfin transcoding is too heavy — serve original files only (direct play). Kiwix is fine. Syncthing is fine. Yggdrasil is fine. Snac2 is fine.

What fits: Yggdrasil mesh routing (~15MB RAM), Syncthing file sync (~30MB RAM), Kiwix-serve for offline knowledge (~20MB RAM), Jellyfin direct-play only (no transcoding, ~80MB RAM), Snac2 federated social (~8MB RAM). Total: ~160MB, leaving 350MB headroom.

What doesn't fit: Transcoding video in Jellyfin (CPU-bound, Pi Zero will drop frames), Mastodon (Rails app, needs 1GB+), Nextcloud (PHP + database, too heavy), anything requiring GPU acceleration.

Upgrade path: Pi 4 or Pi 5 as community anchor nodes — one per neighborhood, handles heavier services. Pi Zero nodes federate up to anchor nodes. Two-tier topology: Zero = leaf, Pi 4/5 = regional backbone.

§ 04BLKMRR Protocol Spec

BLKMRR is a protocol layer on top of existing open tools, not a ground-up implementation. The ARX contribution is the composition: how these tools are configured, how nodes discover each other, how community permissions are managed, and how the image is distributed and maintained. The protocol spec defines the interfaces between layers.

§ 04.1Node Identity & Permissions

Each node has a keypair. Yggdrasil derives the node's IPv6 address from its public key — the address is the identity. No central directory. No DNS dependency. Node announces itself to the mesh via a signed beacon containing: public key, node version, service manifest (which services are running), and community ID.

Permission token. Joining a community mesh requires a signed invitation token from an existing node operator. The token encodes: community ID, issuing node public key, timestamp, and expiry. New nodes present the token on first connect; mesh peers validate the signature. Invalid or expired tokens are rejected.

Community ID. A human-readable string + UUID pair identifying a mesh community. Nodes can belong to multiple communities (e.g., a household node + a neighborhood node + a regional ARX node). Each community has its own Syncthing share folders, Jellyfin library, and social instance.

// BLKMRR peer beacon — broadcast on join { "node_id": "200:1a2b:3c4d:...", // Yggdrasil IPv6 "pubkey": "ed25519:aabbcc...", "version": "blkmrr/0.1.0", "community": "neighborhood-x/uuid", "services": [ "jellyfin", "syncthing", "kiwix", "yggdrasil" ], "invite_token": "sig:base64...", "timestamp": 1746000000 }
§ 04.2Content Sync

Community folders. Each community defines shared Syncthing folders: /media/community (music, video, documents added by any node), /knowledge/zim (ZIM snapshots, synced monthly), /media/local (node-specific, not synced). Folder membership = community membership.

Conflict resolution. Syncthing's built-in conflict handling (version vectors + last-write-wins) handles most cases. Community-defined curation rules (a simple JSON file listing trusted curators per folder) add a lightweight moderation layer without a central authority.

ARX Open Music integration. SoundWeave tracks tagged with the ARX Open Music license are marked as community:free and auto-sync to all nodes in a community mesh. No one owns the signal — every node carries it.

§ 04.3FuelMesh Crossover

BLKMRR nodes that are also mobile (van life, travel) can carry the FuelMesh observation cache and sync it when they dock at a stationary BLKMRR node. Stationary nodes become FuelMesh aggregation points — when you get home, your van's observations flush to the home node, which syncs to the community mesh, which eventually reaches OSM upstream. Passive data contribution with zero user action after initial setup.

The protocol is not clever. The protocol is the composition. Anyone can run these tools. BLKMRR is the image, the configuration, the permission model, and the community contract that makes them into infrastructure.

§ 05Build Phases

BLKMRR builds in layers. Each phase is independently useful — the mesh doesn't need to be complete to deliver value. Phase 0 is literally just a Pi Zero running LibreELEC + Jellyfin. Everything after that is additive.

Phase 0 — Proof
TV Adapter as Media Node
Pi Zero 2W + LibreELEC + Jellyfin. Enclosure designed and printed. USB-powered from TV. Hidden behind bezel. Serves local media to any device on the home network. This is the value proposition that gets people to install it — give them something they want before asking them to run infrastructure. Complete: Q3 2026.
Phase 1 — Sync
Peer-to-Peer Content Sync
Add Syncthing to the image. Two nodes on the same WiFi network discover each other and sync community folders. Community music (SoundWeave / ARX Open Music tagged content) propagates automatically. No user action after pairing. First real mesh behavior — content exists in multiple places simultaneously.
Phase 2 — Mesh
Yggdrasil Encrypted Routing
Add Yggdrasil mesh routing. Nodes get persistent cryptographic addresses. Traffic between nodes is encrypted end-to-end. Permission token system implemented — joining requires an invitation. Community ID system. This is the point where BLKMRR becomes an actual mesh network rather than just a sync setup.
Phase 3 — Knowledge
Offline Knowledge Cache
Add Kiwix-serve + ZIM snapshots (Wikipedia, WikiMed, MDN). Nodes cache community-selected knowledge bases and serve them to any browser on the local network. Monthly update cron. Community decides which ZIMs to carry. The mesh becomes a library.
Phase 4 — Social
Federated Community Layer
Snac2 or Pleroma instance on anchor nodes (Pi 4/5). Zero nodes federate up to anchor. Community has a social feed that's self-hosted, self-moderated, and federated with the broader Fediverse when internet is available. Two-tier topology: Zero leaf nodes + Pi 4/5 anchor nodes per neighborhood.
Phase 5 — Protocol
BLKMRR as Open Spec
BLKMRR node image published as open source (AGPLv3). Protocol spec published as CC BY-SA. Third parties can build compatible nodes on different hardware. FuelMesh relay integration documented. ARX publishes reference hardware guide (BOM + enclosure files + image). The protocol becomes infrastructure — like FuelMesh, not like a product.
